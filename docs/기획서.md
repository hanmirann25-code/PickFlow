# PickFlow — 미니 풀필먼트 관리 콘솔 기획서

> 포트폴리오 프로젝트 기획서 v1.0
> 작성일: 2026-08-28

---

## 0. 이 문서를 읽는 법

이 기획서는 **면접에서 30분 얘기할 거리를 만들기 위한 설계도**입니다.
기능을 많이 넣는 게 목적이 아니라, "이 사람은 데이터 많은 화면과 여러 명이 동시에 쓰는 시스템을 다뤄봤다"를 증명하는 게 목적입니다.

그래서 이 문서는 두 가지를 계속 구분합니다.

- **반드시 만들 것** — 이게 없으면 포트폴리오로서 의미가 없는 부분
- **잘라낼 것** — 있으면 좋지만 시간을 잡아먹고 어필은 안 되는 부분

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | PickFlow |
| 한 줄 소개 | 주문 접수부터 출고까지를 관리하는 풀필먼트 운영 콘솔 |
| 목적 | 프론트엔드 개발자 포지셔닝을 증명하는 포트폴리오 |
| 타깃 독자 | 물류·커머스 솔루션 회사의 개발팀장 / 실무 면접관 |
| 진행 구성 | 6단계 (프롬프트 27개, `docs/단계별-프롬프트.md`) |
| 형태 | 웹 관리자 콘솔 + 현장용 모바일 화면 |
| DB | Oracle (로컬 개발 → Oracle Cloud Always Free 배포) |
| 배포 | 상시 구동형 호스팅 (누구나 데모 계정으로 접속 가능) |

### 이 프로젝트로 증명하려는 것

1. **대용량 데이터를 다루는 화면을 만들 수 있다** — 주문 10만 건에서 안 끊기는 목록
2. **여러 사람이 동시에 써도 데이터가 깨지지 않게 짤 수 있다** — 재고 동시 차감 처리
3. **실시간으로 변하는 화면을 만들 수 있다** — 서버가 밀어주는 데이터로 갱신되는 대시보드
4. **현장 환경을 고려할 수 있다** — 창고에서 네트워크가 끊겨도 작업이 이어지는 모바일 화면
5. **권한과 이력을 설계할 수 있다** — 역할별 화면 제어, 변경 이력 기록

> 이 다섯 개가 이 프로젝트의 전부입니다. 이걸 흐리는 기능은 전부 잘라냅니다.

## 2. 도메인 이해 (용어 정리)

포트폴리오 화면에 쓸 용어를 먼저 정리합니다. 면접에서 이 단어들을 자연스럽게 쓰는 것 자체가 어필입니다.

| 용어 | 뜻 |
|---|---|
| 풀필먼트(Fulfillment) | 주문이 들어온 뒤 상품을 꺼내 포장해 보내기까지의 전 과정 |
| SKU | 상품을 구분하는 최소 단위 코드 (같은 티셔츠라도 색·사이즈가 다르면 다른 SKU) |
| 로케이션 | 창고 안에서 상품이 놓인 위치. 보통 `A-01-03-2`처럼 구역-통로-선반-단 |
| 재고 할당(Allocation) | 주문이 들어오면 그 주문 몫으로 재고를 찜해두는 것. 실제로 빠지진 않음 |
| 가용 재고 | 실제 재고 − 이미 찜해둔 재고. **주문 가능한 진짜 수량** |
| 피킹(Picking) | 창고를 돌며 주문에 필요한 상품을 꺼내오는 작업 |
| 웨이브(Wave) | 여러 주문의 피킹 작업을 한 묶음으로 만든 것. 한 번 돌 때 여러 주문을 같이 처리 |
| 패킹(Packing) | 꺼내온 상품을 검수하고 포장해 송장을 붙이는 작업 |
| 출고 | 포장 완료된 물건을 택배사에 넘기는 것. 이 시점에 재고가 실제로 차감됨 |

### 실제 업무 흐름

```
주문 수집 → 주문 검증 → 재고 할당 → 웨이브 생성 → 피킹 → 패킹 → 출고 → 배송
                          ↓ 재고 부족
                        품절 대기
```

## 3. 범위 (Scope)

### 3-1. 만들 것 (In Scope)

- 주문 목록 / 상세 (대용량 그리드)
- 재고 및 로케이션 조회
- 재고 할당 처리 (동시성 제어 포함)
- 피킹 웨이브 생성 및 배정
- 모바일 피킹 화면 (바코드 스캔, 오프라인 대응)
- 패킹 및 송장번호 등록 (엑셀 대량 업로드)
- 운영 대시보드 (실시간 갱신)
- 로그인 및 역할별 권한 제어
- 변경 이력(감사 로그)

### 3-2. 만들지 않을 것 (Out of Scope) — 명시적으로 자름

| 제외 항목 | 이유 |
|---|---|
| 반품 / 교환 | 흐름이 통째로 하나 더 생김. 기간 두 배 |
| 정산 / 청구 | 화면은 많은데 기술적 어필이 없음 |
| 실제 쇼핑몰 API 연동 | 계정 문제로 데모가 안 돌아감. 가짜 주문 생성기로 대체 |
| 실제 택배사 API | 위와 동일 |
| 입고 / 발주 | 흐름 하나 더. 재고는 초기 데이터로 심어둠 |
| 다국어 | 시간만 먹음 |
| 결제 | 도메인 밖 |

> 면접에서 "왜 반품은 없나요?"를 물으면 이렇게 답하면 됩니다.
> "출고 흐름 하나를 끝까지 완성하는 걸 우선했습니다. 반품은 흐름이 하나 더 생기는 거라, 깊이를 포기하고 넓히는 선택이 될 것 같았습니다."
> **범위를 의도적으로 잘랐다는 것 자체가 실무 감각의 증거입니다.**

### S-03. 주문 목록 — 이 프로젝트의 간판 화면

```
┌──────────────────────────────────────────────────────────────┐
│ 주문 관리                              [ 재고 할당 ] [ 웨이브 생성 ]│
├──────────────────────────────────────────────────────────────┤
│ 기간[2026-08-01 ~ 08-28] 상태[전체 ▾] 채널[전체 ▾] 검색[      ]│
│ 저장된 필터: [오늘 미출고] [지연 주문] [품절 대기]              │
├──────────────────────────────────────────────────────────────┤
│ □ │주문번호  │채널  │수취인│상품수│상태    │주문일시   │경과 │
│ □ │O-20260828│스마트│김○○ │  3  │할당완료│08-28 09:12│2시간│
│ □ │O-20260828│자사몰│이○○ │  1  │피킹중  │08-28 09:10│2시간│
│ ...                                                          │
├──────────────────────────────────────────────────────────────┤
│ 선택 12건  │  전체 103,847건  │  [엑셀 내보내기]              │
└──────────────────────────────────────────────────────────────┘
```

**요구사항**

- 총 10만 건 이상의 데이터를 담고, 스크롤이 끊기지 않아야 함
- 화면에 보이는 행만 실제로 그리는 방식 사용 (가상 스크롤)
- 검색·정렬·필터·페이지 이동은 모두 **서버에서 처리** (브라우저로 다 내려받지 않음)
- 검색어는 입력이 멈춘 뒤 실행 (디바운스 300ms)
- 필터 조건은 주소창(URL)에 반영 → 새로고침해도 유지, 링크 공유 가능
- 체크박스 다중 선택 후 일괄 작업 (할당, 보류, 취소)
- 표 헤더 고정, 주문번호 열 고정(가로 스크롤 시)
- 열 너비 조절 및 표시 열 선택, 설정은 사용자별 저장

**접근성 기준 (기본으로 지킬 것)**

- 표는 `<table>` + `<th scope>` 로 마크업, 정렬 상태는 `aria-sort`로 전달
- 체크박스마다 어떤 행인지 알 수 있는 레이블 제공
- 키보드만으로 행 이동·선택·일괄작업 실행 가능
- 포커스 표시 유지, 가상 스크롤 구간에서도 포커스가 사라지지 않게 처리

### S-05. 재고 현황

```
SKU        상품명           실재고  할당됨  가용   로케이션
SKU-10023  기본 티셔츠 M/블랙  120     45     75   A-01-03-2 외 2곳
```

- **가용 재고 = 실재고 − 할당됨** 을 화면에서 명확히 보여줄 것 (도메인 이해도 어필 포인트)
- 가용 재고 0 이하는 경고색 + 텍스트로도 표시 (색만으로 정보 전달 금지)
- 로케이션별 분산 재고 펼쳐보기

### S-06. 웨이브 생성

- 주문 목록에서 선택 → "웨이브 생성"
- 생성 시 각 주문 상품을 **로케이션 순서대로 정렬**해 피킹 동선을 만들어줌
  (A-01 → A-02 → B-01 순. 이 정렬 로직 하나가 "물류 이해했네" 소리를 만듭니다)
- 작업자 배정
- 웨이브 상태: 대기 → 진행중 → 완료

### S-08. 송장 일괄 업로드

- 엑셀 파일 드래그 업로드 (수천 행 가정)
- 화면이 멈추지 않게 백그라운드에서 파싱 (Web Worker)
- 진행률 표시
- 검증 결과를 **성공 / 실패로 나눠 표시**, 실패 행만 사유와 함께 목록으로
- 실패 행만 담긴 엑셀 다시 내려받기 → 고쳐서 재업로드
- 부분 성공 처리 (5,000건 중 4,987건만 반영)

> 이 화면은 "실무 안 해본 사람은 절대 이렇게 안 만든다"는 인상을 줍니다. 오류 행 되돌려주기가 핵심.

### S-09. 모바일 피킹 — 차별화 화면

```
┌─────────────────────┐
│ 웨이브 W-0821  3/12 │
├─────────────────────┤
│                     │
│   A-01-03-2         │  ← 위치를 크게
│                     │
│   기본 티셔츠 M/블랙 │
│   SKU-10023         │
│                     │
│      2 개           │  ← 수량을 더 크게
│                     │
│  [  바코드 스캔  ]   │
│  [ 수동 입력 ] [건너뛰기]│
├─────────────────────┤
│ ● 오프라인 · 3건 대기중│
└─────────────────────┘
```

**요구사항**

- 장갑 낀 손 기준: 터치 영역 최소 48×48px, 한 화면에 한 작업만
- 카메라로 바코드 인식 (BarcodeDetector API, 미지원 브라우저는 라이브러리로 대체)
- 스캔한 바코드가 지시된 SKU와 다르면 즉시 오류 (진동 + 색 + 텍스트)
- **오프라인 대응**: 창고 안쪽은 신호가 약함
  - 작업 결과를 브라우저 저장소(IndexedDB)에 먼저 쌓음
  - 연결 복구되면 자동 전송
  - 같은 요청이 두 번 가도 한 번만 처리되게 요청마다 고유 키 부여(멱등 처리)
  - 화면 상단에 온라인/오프라인·대기 건수 항상 표시
- 세로 고정, 큰 글씨, 밝은 곳에서도 보이는 대비
- 안드로이드 크롬 / iOS 사파리 / 인앱 브라우저 모두 확인

### S-02. 운영 대시보드

- 오늘 주문 / 출고 / 미출고 / 지연 건수 (실시간 갱신)
- 시간대별 출고 추이 차트
- 재고 부족 임박 SKU 목록
- 작업자별 피킹 진행률
- 데이터는 서버가 밀어주는 방식(SSE)으로 갱신. 폴링 아님
- 연결이 끊겼다 붙으면 놓친 구간 다시 받아오기

```
  id, order_id, courier, tracking_no, shipped_at, created_by

inventory_transactions   ← 재고 변동 이력 (되돌리기·추적용)
  id, product_id, location_id, delta, type(ALLOCATE|PICK|SHIP|ADJUST),
  ref_type, ref_id, created_by, created_at

audit_logs
  id, user_id, action, target_type, target_id, before(json), after(json), created_at

idempotency_keys        ← 모바일 중복 전송 방지
  key, user_id, response(json), created_at
```

### 오라클 적용 지침

스키마는 위 구조 그대로 가되, 오라클 문법에 맞춰 다음을 지킵니다.

| 항목 | 적용 |
|---|---|
| 문자열 | `VARCHAR2(n CHAR)` — 한글 길이 문제 방지 |
| 숫자 | `NUMBER(10)`, 금액은 `NUMBER(15,2)` |
| 날짜 | `TIMESTAMP WITH TIME ZONE` |
| JSON | `CLOB` + `IS JSON` 제약 (감사 로그의 before/after) |
| PK 채번 | `GENERATED BY DEFAULT AS IDENTITY` |
| 주문번호 채번 | 시퀀스 + `O-YYYYMMDD-` 접두 조합 |
| 대소문자 | 테이블·컬럼명은 전부 대문자 스네이크(`ORDER_ITEMS`)로 통일 |

**꼭 만들 인덱스** (없으면 10만 건에서 목록이 느려집니다)

```sql
-- 주문 목록 기본 정렬 + 상태 필터
CREATE INDEX IX_ORDERS_STATUS_DATE ON ORDERS(STATUS, ORDERED_AT DESC);
-- 채널별 조회
CREATE INDEX IX_ORDERS_CHANNEL_DATE ON ORDERS(CHANNEL, ORDERED_AT DESC);
-- 재고 조회 (유니크 제약 겸용)
CREATE UNIQUE INDEX UX_INV_PROD_LOC ON INVENTORY(PRODUCT_ID, LOCATION_ID);
-- 피킹 작업 동선 정렬
CREATE INDEX IX_TASKS_WAVE_SORT ON PICKING_TASKS(WAVE_ID, SORT_ORDER);
```

> 실행 계획(`EXPLAIN PLAN`)을 인덱스 적용 전후로 캡처해두세요. README에 붙이면 그 자체가 강력한 증거입니다.

### 주문 상태 흐름

```
RECEIVED(접수)
   ├─ 재고 충분 ─→ ALLOCATED(할당완료) → PICKING(피킹중) → PACKED(패킹완료) → SHIPPED(출고완료)
   └─ 재고 부족 ─→ BACKORDER(품절대기) ─(입고 시)→ ALLOCATED
   
어느 단계든 → HOLD(보류) / CANCELLED(취소)  ※ SHIPPED 이후는 취소 불가
```

**규칙**

- 상태는 정해진 방향으로만 이동. 역방향·건너뛰기 금지 (서버에서 검증)
- 취소 시 할당된 재고는 반드시 원복
- 상태 변경은 전부 `audit_logs`에 기록

## 7. 기술적 도전 과제 — 면접에서 말할 5가지

이 프로젝트의 진짜 내용물입니다. 각 항목은 **README에 "문제 → 원인 → 해결 → 수치" 4단 구성으로** 정리합니다.

### ① 10만 건 그리드 성능

- 문제: 데이터가 많아지면 브라우저가 수만 개 DOM을 그리다 멈춤
- 해결: 화면에 보이는 30여 행만 렌더링 (가상 스크롤) + 서버 페이징·필터·정렬
- 측정: 초기 렌더 시간, 스크롤 프레임(FPS), 필터 응답 시간
- 목표 수치 예: 초기 렌더 3,200ms → 240ms / 스크롤 24fps → 58fps

### ② 재고 동시 차감 (제일 강력한 무기)

- 문제: 남은 재고 1개를 두 운영자가 동시에 할당하면 재고가 −1이 됨
- 시연 방법: **데모 화면에 "동시 요청 10개 발사" 버튼을 만들어 직접 보여주기**
- 해결 (오라클 기준):
  - 할당 대상 재고 행을 `SELECT ... FOR UPDATE`로 잠그고 처리 — 다른 요청은 대기
  - 조건부 갱신으로 이중 방어: `UPDATE INVENTORY SET QTY_ALLOCATED = QTY_ALLOCATED + :n WHERE ... AND QTY_ON_HAND - QTY_ALLOCATED >= :n`
    → 갱신된 행 수가 0이면 재고 부족으로 판단
  - 전체 로직을 **PL/SQL 저장 프로시저**로 만들어 DB 안에서 한 번에 처리 (왕복 횟수 감소 + 원자성 보장)
  - 여러 상품을 한 트랜잭션으로 묶고, 하나라도 실패하면 `ROLLBACK`
  - 잠그는 순서를 항상 `PRODUCT_ID` 오름차순으로 고정 (교착 상태 방지)
  - 응답 지연이 길어지지 않게 `FOR UPDATE WAIT 3` 로 대기 시간 제한
  - 부분 할당 정책을 명시 (전량 아니면 할당 안 함 vs 가능한 만큼만)
- 어필 포인트: 프론트엔드만 하는 사람은 이 문제를 **인식조차 못 합니다**. 여기에 오라클 프로시저까지 붙으면 물류 솔루션 회사 면접관 기준으로 가장 확실한 신호가 됩니다

### ③ 실시간 대시보드

- SSE로 서버가 변경 이벤트를 밀어줌
- 끊겼다 붙었을 때 마지막 수신 이벤트 ID 기준으로 놓친 구간 재조회
- 초당 수십 건이 들어와도 화면이 버벅이지 않게 묶어서 갱신 (배치 업데이트)

### ④ 오프라인 피킹

- 작업 결과를 IndexedDB 큐에 먼저 저장 → 온라인 복구 시 순차 전송
- 요청마다 고유 키를 붙여 중복 전송돼도 한 번만 처리
- 전송 실패 시 재시도 간격을 점점 늘림
- 시연: 개발자도구에서 네트워크 끊고 작업 → 다시 켜면 자동 반영되는 장면

### ⑤ 대량 엑셀 처리

- Web Worker에서 파싱해 화면 멈춤 방지
- 행 단위 검증(스키마 검증 라이브러리 사용) 후 성공/실패 분리
- 실패 행만 사유 붙여 엑셀로 다시 제공

## 8. 실행 구조 설계 — 하네스 · 그래프 · 루프 · 훅

7장이 "무엇을 증명할 것인가"라면, 이 장은 **"그걸 어떤 구조로 굴릴 것인가"**입니다.

---

### 8-1. 하네스 — 주장을 증명하는 장치

포트폴리오의 주장("10만 건에서 안 끊긴다", "동시 요청에도 재고가 안 깨진다")은 **재현 가능해야** 의미가 있습니다. 하네스는 그 재현 장치입니다.

`harness/` 폴더에 독립 실행 스크립트로 둡니다. 앱 코드와 섞지 않습니다.

| 하네스 | 실행 | 하는 일 | 합격 기준 |
|---|---|---|---|
| **seed** | `harness:seed --orders 100000` | 상품 5,000 / 로케이션 2,000 / 주문 10만 / 주문상품 25만 건 생성 | 5분 이내 완료, 재고 합계 일치 |
| **concurrency** | `harness:concurrency --sku SKU-10023 --requests 10` | 재고 1개 상품에 할당 요청을 동시 발사 | 성공 1 / 실패 9, 최종 가용 재고 0, 마이너스 없음 |
| **perf** | `harness:perf` | 목록 첫 렌더·스크롤 프레임·필터 응답·쿼리 시간 측정 | 렌더 300ms 이하, 55fps 이상, 필터 500ms 이하 |
| **offline** | `harness:offline --tasks 20` | 네트워크 차단 상태로 작업 쌓고 복구 후 동기화 | 정확히 20건 반영, 중복 0건 |
| **invariants** | `harness:invariants` | 데이터 정합성 조건 8가지 일괄 검사 (8-5 참고) | 8개 전부 통과 |

**결과 처리**

```
harness/results/2026-08-28-perf.json
harness/results/2026-08-28-concurrency.json
        ↓  harness:report
README.md 의 성과 지표 표를 자동 갱신
```

README에 `<!-- HARNESS:START -->` ~ `<!-- HARNESS:END -->` 마커를 두고 그 사이를 갈아끼우는 방식.

> **이게 이 프로젝트의 숨은 무기입니다.** 면접에서 "이 수치는 어떻게 나온 건가요?" 하면 "명령어 하나 돌리면 지금 다시 나옵니다"라고 답할 수 있습니다. 적어놓은 수치와 재현되는 수치는 무게가 다릅니다.

**시연용 연결**: concurrency 하네스는 관리자 화면의 "동시 요청 10개 발사" 버튼과 같은 로직을 씁니다. 스크립트로도, 화면에서도 돌아가게.

### 8-2. 그래프 — 상태 전이를 한 곳에서 정의

지금 기획서의 상태 흐름은 문서 속 그림일 뿐입니다. **코드 한 곳에서 강제**해야 설계가 됩니다.

**정의 파일 하나** (`lib/order-graph.ts`)

```ts
// 이 표가 유일한 진실. 서버도 화면도 여기만 본다.
export const ORDER_TRANSITIONS = [
  { from: 'RECEIVED',  to: 'ALLOCATED', label: '재고 할당',
    roles: ['ADMIN','OPERATOR'], guard: 'hasEnoughStock',
    effects: ['audit','inventoryTx'] },
  { from: 'RECEIVED',  to: 'BACKORDER', label: '품절 대기',
    roles: ['ADMIN','OPERATOR'], effects: ['audit'] },
  { from: 'ALLOCATED', to: 'PICKING',   label: '피킹 시작',
    roles: ['ADMIN','OPERATOR'], effects: ['audit','emit'] },
  { from: 'PICKING',   to: 'PACKED',    label: '패킹 완료',
    roles: ['ADMIN','OPERATOR'], guard: 'allItemsPicked',
    effects: ['audit','emit'] },
  { from: 'PACKED',    to: 'SHIPPED',   label: '출고 확정',
    roles: ['ADMIN','OPERATOR'], guard: 'hasTrackingNo',
    effects: ['audit','inventoryTx','emit'] },
  // 취소·보류는 별도 정의. SHIPPED 이후 취소 불가
] as const;
```

**이 표를 세 곳에서 씁니다**

1. **서버 전이 함수** — 상태 변경은 오직 `transition(orderId, to, user)` 하나로만. 표에 없는 전이는 거부하고 거부 사유를 남김
2. **화면 액션 버튼** — 현재 상태 + 내 역할로 표를 걸러서 버튼을 **자동 생성**. 화면과 서버가 어긋날 수 없음
3. **다이어그램** — 표에서 Mermaid 문법을 뽑아 README에 삽입. 코드가 바뀌면 그림도 바뀜

**또 하나의 그래프: 피킹 동선**
웨이브 생성 시 주문 상품들을 로케이션 정렬 순서(`locations.sort_order`)대로 이어 경로를 만듭니다. 최단 경로까지 갈 필요 없이 **한 방향으로 훑는 순회**면 충분하고, 그 판단 근거를 README에 쓰면 됩니다.

### 8-3. 루프 — 셋, 각각 종료 조건을 명시

루프 설계의 핵심은 기능이 아니라 **"언제 멈추는가, 실패하면 어떻게 되는가"**입니다. 이걸 안 정하면 중복 처리나 무한 재시도로 반드시 터집니다.

| | ① 오프라인 동기화 루프 | ② 실시간 이벤트 루프 | ③ 피킹 작업 루프 |
|---|---|---|---|
| **트리거** | 온라인 복구 / 앱 포그라운드 진입 / 30초 주기 | 상태 전이 발생 | 작업 확정 완료 |
| **한 사이클** | 큐에서 1건 꺼냄 → 전송 → 성공이면 삭제 | 이벤트 저장 → 구독자에게 전달 | 다음 작업 조회 → 표시 → 스캔 검증 → 확정 |
| **종료 조건** | 큐가 비면 종료 | 연결 종료 시 | 웨이브 내 작업 소진 |
| **실패 처리** | 대기 후 재시도 (2초→4초→8초…) | 연결 끊김으로 처리, 재연결 시도 | 스캔 불일치는 오류 표시 후 같은 작업 유지 |
| **재시도 상한** | 5회 실패 시 "전송 실패" 표시하고 사용자 판단에 맡김 | 무제한 재연결하되 간격 최대 30초 | 3회 불일치 시 건너뛰기 안내 |
| **중복 방지** | 요청마다 고유 키(멱등키), 서버는 같은 키 재수신 시 이전 결과 반환 | 마지막 수신 이벤트 ID 기준 재조회 | 작업 상태로 이미 처리분 필터 |
| **관측** | 화면 상단에 대기 건수 상시 표시 | 연결 상태 아이콘 | 진행률 `3/12` |

**건너뛴 작업 처리 규칙 (미리 정해둘 것)**: 건너뛴 피킹 작업은 웨이브 끝에 다시 붙이고, 두 번째 건너뛰기부터는 `SKIPPED`로 확정한 뒤 해당 주문을 보류 상태로 돌립니다.

### 8-4. 훅 — 상태 전이에 따라붙는 일들

상태가 바뀔 때마다 따라와야 하는 일이 세 가지입니다. 이걸 화면·API 곳곳에 흩뿌리면 반드시 누락이 생깁니다. **전이 함수 한 곳에서만** 실행합니다.

| 훅 | 하는 일 | 실행 시점 |
|---|---|---|
| `audit` | 누가·언제·무엇을 바꿨는지 기록 (변경 전/후 값 포함) | **트랜잭션 안** |
| `inventoryTx` | 재고 변동 이력 기록 (할당 / 피킹 / 출고 / 조정) | **트랜잭션 안** |
| `emit` | 실시간 이벤트 발행 (대시보드·목록 갱신용) | **커밋 이후** |

**여기서 갈리는 부분**: 이벤트 발행을 트랜잭션 안에서 하면, 롤백됐는데 알림만 나가는 상황이 생깁니다. 그래서 커밋이 끝난 뒤에 발행합니다. 이 구분을 설명할 수 있으면 그것만으로도 설계 감각이 증명됩니다.

**훅 실패 정책**: `audit`·`inventoryTx`가 실패하면 전체 롤백(기록 없는 변경은 허용 안 함). `emit`이 실패하면 로그만 남기고 진행(실시간 갱신이 안 될 뿐, 데이터는 정상).

리액트 커스텀 훅(`useOrderGrid`, `useScanner` 등)은 구현하면서 자연스럽게 나오는 것이라 별도 설계가 필요 없습니다.

### 8-5. 검증 기준을 세우는 방법

하네스 표에 합격 기준이 한 줄씩 적혀 있지만, **그 숫자를 왜 그렇게 잡았는지**가 빠져 있으면 기준이 아니라 희망사항입니다. 기준은 다음 네 가지를 갖춰야 기준이 됩니다.

1. **숫자에 근거가 있을 것** — "빨라야 한다"가 아니라 "사람이 즉시로 느끼는 한계가 0.3초라서 300ms"
2. **측정 조건이 고정돼 있을 것** — 같은 데이터, 같은 환경, 같은 횟수로 재야 비교가 됨
3. **통과·실패를 사람이 판단하지 않을 것** — 하네스가 판정하고, 실패면 종료 코드 1을 반환
4. **미달했을 때 할 일이 정해져 있을 것** — 고치거나, 못 고치면 한계로 기록하거나

기준은 성격이 다른 세 종류로 나눠서 세웁니다.

#### ① 정합성 기준 (불변식) — 하나라도 깨지면 실패

"데이터가 안 깨진다"를 증명하는 가장 확실한 방법은, **항상 참이어야 하는 조건을 목록으로 만들어놓고 매번 검사**하는 것입니다. `harness:invariants` 명령 하나로 전부 확인합니다.

| # | 항상 참이어야 하는 조건 |
|---|---|
| 1 | 모든 재고 행에서 `0 ≤ QTY_ALLOCATED ≤ QTY_ON_HAND` |
| 2 | 가용 재고(`ON_HAND − ALLOCATED`)가 음수인 행이 0건 |
| 3 | 상품별 `ORDER_ITEMS.ALLOCATED_QTY` 합계 = `INVENTORY.QTY_ALLOCATED` 합계 |
| 4 | `SHIPPED` 주문의 모든 항목에서 `PICKED_QTY = QTY` |
| 5 | 상태 변경 횟수 = `AUDIT_LOGS`의 상태 변경 기록 수 (기록 없는 변경 0건) |
| 6 | 재고 증감 총합 = `INVENTORY_TRANSACTIONS`의 델타 총합 |
| 7 | 완료된 웨이브에 `PENDING` 상태 작업 0건 |
| 8 | 같은 멱등키로 두 번 처리된 건 0건 |

동시성 하네스는 **실행 후 반드시 이 검사를 이어서 돌립니다.** 요청 10개 중 1개만 성공했다는 것보다, "그 뒤에도 8개 조건이 전부 참이다"가 훨씬 강한 증거입니다.

#### ② 성능 기준 — 값과 근거를 함께

| 항목 | 기준 | 근거 |
|---|---|---|
| 주문 목록 첫 렌더 | 300ms 이하 | 사람이 "즉시"로 느끼는 구간이 대략 0.1~0.3초 |
| 필터·검색 응답 | 500ms 이하 | 1초를 넘기면 작업 흐름이 끊긴다고 느낌 |
| 스크롤 프레임 | 55fps 이상 | 부드러움 기준 60fps = 프레임당 16.7ms |
| 스캔 후 다음 작업 표시 | 300ms 이하 | 현장에서 연속 작업 리듬이 끊기지 않는 선 |
| 엑셀 5,000행 처리 | 한 번에 50ms 넘게 화면을 붙잡는 작업 0건 | 그 이상이면 클릭이 씹히는 게 체감됨 |
| 재고 할당 API | 1건 200ms 이하 / 동시 10건에서 1초 이하 | 버튼을 누른 뒤 결과가 뜰 때까지 기다린다고 느끼지 않는 선. 동시 10건은 `FOR UPDATE WAIT 3`의 대기 상한 안에서 순차 처리돼야 함 |

**측정 조건 (고정)**

- 데이터: 주문 10만 · 주문상품 25만 건, 시드값 고정 (매번 같은 데이터)

- 반복: 5회 측정, **중앙값과 최악값을 함께 기록**. 평균은 쓰지 않음 — 한 번 크게 튄 값을 숨기기 때문
- 캐시: 첫 방문(캐시 비움)과 재방문을 따로 기록

**미달했을 때**: 두 번 개선을 시도하고도 못 맞추면, README의 "알려진 한계"에 수치와 이유를 그대로 적습니다. 숨기는 것보다 적는 쪽이 신뢰를 얻습니다. 면접에서도 "여긴 이래서 못 맞췄고, 다음엔 이렇게 접근하겠다"가 좋은 답변입니다.

### 왜 Vercel이 아닌가 (면접에서 물어보면 답할 내용)

Vercel은 요청이 올 때마다 서버가 잠깐 떴다 사라지는 구조입니다. 그래서 DB 연결을 미리 만들어두고 재사용하는 **커넥션 풀**의 이점이 사라집니다. 오라클은 연결 하나 맺는 비용이 큰 편이라, 요청마다 새로 연결하면 응답이 눈에 띄게 느려집니다.
→ 서버가 계속 떠 있는 곳에 올려서 커넥션 풀을 유지하는 구성으로 갑니다. 이 판단 자체가 면접 답변 소재입니다.

### 오라클 연결 시 미리 알아둘 것

- Oracle Cloud의 Autonomous Database는 기본적으로 **지갑(Wallet) 파일**로 접속합니다. 파일을 서버에 두고 경로를 환경변수로 지정하는 방식.
- 접속 정보(사용자, 비밀번호, 지갑 경로)는 **처음부터 전부 환경변수로 분리**. 로컬↔클라우드 전환이 설정값 교체만으로 되게.
- 커넥션 풀은 앱 시작 시 1회만 생성. Next.js 개발 모드에서 매번 새로 만들어지지 않게 전역 객체에 캐싱.
- 무료 DB는 장기간 사용하지 않으면 자동 중지되는 정책이 있습니다. 구직 기간 중 꺼지지 않도록 생성 시 약관을 확인하고, 주기적으로 접속할 것.

### 기본 품질 기준 (전 화면 공통)

- 웹 접근성: 시맨틱 태그 우선, 폼 레이블 연결, 키보드 조작, 포커스 표시 유지
- 반응형: 데스크톱 / 태블릿 / 모바일
- 호환성: 안드로이드 크롬, iOS 사파리, 인앱 브라우저(카카오·네이버)에서 동작 확인
- 다크모드는 선택 사항 (시간 남으면)

## 10. 개발 단계

기한을 정해두지 않는다. **한 단계를 완료 기준까지 통과시킨 뒤 다음으로 넘어간다.**
각 단계에 대응하는 프롬프트는 `docs/단계별-프롬프트.md`에 있다.

| 단계 | 목표 | 완료 기준 | 프롬프트 |
|---|---|---|---|
| **1단계** | **인프라 관통** | Oracle Cloud 계정 생성, 무료 DB 발급, **로컬 앱 → 클라우드 DB 접속 성공**, 호스팅에 빈 화면 배포까지 완료 | P1~P3 |
| **2단계** | 기반 | 스키마 생성 SQL, 인덱스, 로그인(Auth.js), 역할별 권한, 공통 레이아웃 | P4~P7 |
| **3단계** | 주문 그리드 | 더미 데이터 10만 건 생성기, 목록 화면, 서버 페이징·필터, 가상 스크롤, **성능 측정 전/후 기록** | P8~P12 |
| **4단계** | 재고·할당 | 재고 화면, PL/SQL 할당 프로시저, 동시성 처리, 동시 요청 시연 버튼, 웨이브 생성 | P13~P18 |
| **5단계** | 모바일 피킹 | 모바일 화면, 바코드 스캔, 오프라인 큐, 중복 방지, 실기기 테스트 | P19~P22 |
| **6단계** | 마무리 | 대시보드 실시간, 엑셀 업로드, 감사 로그, README, 데모 영상 | P23~P27 |

### 하네스 배치

| 단계 | 만들 하네스 |
|---|---|
| 3단계 | seed (데이터 10만 건) + perf 1차 측정 |
| 4단계 | concurrency + invariants |
| 5단계 | offline |
| 6단계 | perf 최종 측정 + report (README 자동 갱신) |

기능을 먼저 만들고 하네스를 나중에 붙이지 마세요. **하네스가 먼저 있어야 그 기능이 제대로 됐는지 알 수 있습니다.**

### 절대 어기면 안 되는 세 가지

1. **1단계를 가장 먼저, 끝까지 뚫을 것.** 화면이 텅 비어 있어도 상관없습니다. "클라우드 DB에 붙고, 배포된 주소가 열린다"까지 확인하세요. 지갑 파일, 방화벽, 접속 규칙에서 반드시 한 번은 막힙니다. 다 만들어놓고 마지막에 발견하면 프로젝트가 통째로 날아갑니다.
2. **3단계의 더미 데이터 10만 건 생성기를 건너뛰지 말 것.** 이게 없으면 이 프로젝트는 그냥 예쁜 관리자 화면이 됩니다.
3. **단계를 앞당기려고 완료 기준을 낮추지 말 것.** 통과 못 한 단계를 안고 다음으로 가면 뒤에서 두 배로 돌아옵니다.
